# Build zero-touch agent machines on Debian 13

> Research report written on 2026-10-05 that led to agos' design. Some recommendations have since been refined in `docs/spec.md`, which wins where they differ.

You can build a custom Linux image that boots, configures itself and gives an AI agent a full graphical desktop with no human input, using only maintained parts, and nobody ships one yet. Computer-use environments come as Docker images or metered cloud sandboxes, and the two existing "agent distros", AgenticLinux (Fedora bootc) and Omarchy (Arch), target CLI coding agents with no GUI-automation layer ([AgenticLinux](https://ericcurtin.github.io/2026/09/18/announcing-agenticlinux/); [MindStudio on Omarchy](https://www.mindstudio.ai/blog/what-is-omarchy-linux)). The strongest design is **Debian 13 "trixie"** with an **X11 display served by KasmVNC's Xvnc**, one process that is both the agent's screen and the human's browser viewer, plus an XFCE session started by systemd with no display manager. On top sits a **small custom control daemon (working name `agentd`)** that adds what no maintained project offers: a stable coordinate contract, adapters for Anthropic, OpenAI and Gemini, MCP and REST transports, accessibility trees, audit logs and a human-takeover lease. Configuration arrives through a **cloud-init NoCloud seed**, and humans reach the machine through **Tailscale**, with `tailscale serve` in front of KasmVNC and tagged OAuth credentials. **One mkosi recipe** produces the hybrid ISO and the raw, qcow2, OVA, VHDX and UTM images for x86_64 and arm64 on GitHub's free native arm64 runners. Deliver it VM-first through a Proxmox one-liner, and put a thin immutable host under it on bare metal. The reason is that prompt injection is unsolved: visual injection deceived computer-use agents up to **51%** of the time in VPI-Bench ([VPI-Bench](https://arxiv.org/pdf/2506.02456)). The hypervisor, an egress allowlist enforced outside the guest, and keeping valuable credentials out of the guest are therefore the real security boundary. Only three blockers cannot be fixed in software and must be designed around: BIOS halt and power-restore settings on physical machines, Secure Boot MOK enrollment (which rules out DKMS modules), and the Raspberry Pi 5's lack of maintained UEFI firmware. Against the earlier suggestion of NixOS + X11 + cloud-init NoCloud + Tailscale, this research **overturns NixOS** and **confirms the other three with refinements**.

## Users want an always-on agent computer, and nobody ships one as an image

Every major open computer-use environment runs the same stack, so a new image should match it rather than reinvent it. Anthropic's reference demo is `ubuntu:22.04` with Xvfb, xdotool, scrot, the Mutter window manager, x11vnc and noVNC, at a default 1024×768 ([Anthropic Dockerfile](https://github.com/anthropics/claude-quickstarts/blob/main/computer-use-demo/Dockerfile)). E2B Desktop is Ubuntu 22.04 with Xvfb, XFCE, x11vnc and a forked noVNC inside Firecracker microVMs ([E2B template](https://github.com/e2b-dev/desktop/blob/main/template/template.py)). Bytebot (now archived) and Cua's XFCE container use the same recipe ([Bytebot Dockerfile](https://github.com/bytebot-ai/bytebot/blob/main/packages/bytebotd/Dockerfile); [Cua XFCE docs](https://cua.ai/docs/cua/reference/desktop-sandbox/linux-container/xfce)). OSWorld's benchmark VMs explicitly force Xorg instead of Wayland ([OSWorld server README](https://github.com/xlang-ai/osworld-server/blob/main/README.md)). The projects differ in isolation (Docker, Firecracker, gVisor or full KVM), persistence (none, pause/resume, or snapshot/fork) and control API (none, a custom REST/gRPC daemon, or MCP), not in the display stack. They also share weak defaults. Anthropic's demo runs x11vnc with `-nopw` and gives its user passwordless sudo, and its README concedes the components are "weakly separated" and single-session ([x11vnc_startup.sh](https://github.com/anthropics/claude-quickstarts/blob/main/computer-use-demo/image/x11vnc_startup.sh); [computer-use-demo README](https://github.com/anthropics/claude-quickstarts/tree/main/computer-use-demo)).

Hosted sandboxes fill part of the gap, but they come with caps and vendor risk. E2B's desktop sandboxes stop at **1 hour on Hobby and 24 hours on Pro** and are CPU-only ([E2B pricing](https://e2b.dev/pricing)). Daytona moved core development to a private codebase and archived its open repo in 2026 ([Daytona](https://github.com/daytonaio/daytona)). Scrapybara shut down its desktops in October 2025 and deleted running VMs ([Scrapybara](https://x.com/scrapybara/status/1971655785869726110)). Upstash compared 15 sandbox providers in September 2026 and found that only a handful offer any GUI. It also found that wall-clock billing makes an agent hour spent mostly waiting **2.6× to 19×** more expensive than active-CPU billing ([Upstash](https://upstash.com/blog/ai-agent-sandbox-providers-compared-2026)). That is why practitioners self-host on Mac minis, old Xeons and Proxmox clusters. They insist on "a hardened QEMU/KVM VM that reaches the internet but has no route to the host, the LAN, or any other private address" ([HN](https://news.ycombinator.com/item?id=49214825)). The exposure of thousands of OpenClaw gateways that listened on every interface made private networking a first-class requirement ([Coder](https://coder.com/blog/why-i-ditched-openclaw-and-built-a-more-secure-ai-agent-on-blink-mac-mini)).

User demand is consistent across projects. The requests with the most reactions are human-in-the-loop takeover for logins, MFA and CAPTCHAs ([browser-use #221](https://github.com/browser-use/browser-use/issues/221)), and persistent sessions with logged-in browser profiles. Manus called ephemeral sandboxes "fine for one-shots, fatal for any recurring workflow" ([idlen.io](https://www.idlen.io/news/manus-cloud-computer-persistent-virtual-machine-ai-agents-247-april-2026/)). Next come credential brokering that keeps secrets away from the agent ([E2B #1160](https://github.com/e2b-dev/E2B/issues/1160)), local and open-model support ([Bytebot issues](https://github.com/bytebot-ai/bytebot/issues)), snapshot and fork, recording, MCP access to the computer itself ([claude-quickstarts #209](https://github.com/anthropics/claude-quickstarts/issues/209)), egress control and prebuilt images. The recurring pain points are just as consistent. Wayland breaks xdotool-style tooling: Cua rates X11 "Supported" but most Wayland compositors only "Experimental" or "Supported with limits" ([Cua platform support](https://github.com/trycua/cua/blob/main/docs/content/docs/cua-driver/concepts/platform-support.mdx)). Other complaints are screenshot and coordinate scaling mismatches, slow VNC, keyring and first-run popups, bot detection, and crashes in long sessions. Since version 136, Chrome also refuses CDP control on the default profile ([browser-use #1520](https://github.com/browser-use/browser-use/issues/1520)).

The closest products each miss part of this combination. AgenticLinux is a Fedora 44 bootc image with a read-only root, atomic rollback, and Claude Code and Codex preinstalled, but its announcement describes no screenshot/input API and no remote viewer ([AgenticLinux](https://ericcurtin.github.io/2026/09/18/announcing-agenticlinux/)). Omarchy ships "no GUI automation tools" ([MindStudio](https://www.mindstudio.ai/blog/what-is-omarchy-linux)). Cua Spaces offers multiplayer takeover and an encrypted keyvault, but it is macOS-first and FSL-licensed ([Cua](https://github.com/trycua/cua)). **No widely adopted installable image turns a bare-metal box or VM into an unattended, remotely viewable computer-use host**, least of all for Linux homelabs.

### Zero required input is achievable, zero possible input is not

Every software-level blocker in this research has a documented fix (see the hardening section). So the answer to "is it possible" is yes, with three hardware exceptions and two human ones. Physical BIOSes may halt on "Press F1", or stay off after a power loss, until someone changes a vendor-specific setting once ([HPE community](https://community.hpe.com/t5/proliant-servers-ml-dl-sl/disable-keyboard-detection-in-bios/m-p/2803711/highlight/true)). Secure Boot MOK enrollment deliberately requires a person at the console, so the image must never depend on out-of-tree kernel modules ([Debian Wiki SecureBoot](https://wiki.debian.org/SecureBoot)). The Raspberry Pi 5 has no maintained UEFI firmware and needs its own image ([worproject/rpi5-uefi](https://github.com/worproject/rpi5-uefi)). Apple Silicon bare metal is reachable only through Fedora Asahi Remix, and only on M1–M3 ([Fedora Magazine](https://fedoramagazine.org/fedora-asahi-remix-43-is-now-available/); [Asahi blog](https://asahilinux.org/2026/09/m2-episode-1/)).

On the human side, MFA and CAPTCHA walls need someone to take over, and every model vendor tells developers to have a human confirm consequential actions ([Claude computer use docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)). The right target is therefore **zero *required* input**: the machine boots, heals and works alone, while takeover and approvals stay available out of band. In Alibaba's AgentBay study, human interventions of 15–30 seconds raised task success above 95% ([AgentBay](https://arxiv.org/html/2512.04367v1)).

## Debian 13 beats NixOS, Ubuntu and Fedora as the base

The base distro has three jobs. It must keep shipping an X server, carry current non-snap browsers on both architectures, and deliver security updates for years. Desktop Linux is leaving X11 fast. GNOME 50 removed its X11 session in March 2026 ([The Register](https://www.theregister.com/2026/03/19/gnome_50/)), and KDE Plasma 6.8 goes Wayland-only on October 14, 2026 ([Phoronix](https://www.phoronix.com/news/KDE-Plasma-Wayland-Ex-X11)). RHEL 10 and CentOS Stream 10 removed Xorg, including Xvfb ([Phoronix](https://www.phoronix.com/news/RHEL10-Removing-X.Org); [adoptium #3851](https://github.com/adoptium/infrastructure/issues/3851)), and openSUSE Leap 16 dropped the Xorg server ([Leap 16 release notes](https://susedoc.github.io/release-notes/leap-16.0/html/release-notes/index.html)).

The X server itself is still maintained: version 21.1.24 shipped security fixes in July 2026 ([xorg-announce](https://lists.x.org/archives/xorg-announce/2026-July/003718.html)). GNOME's developers expect distros to keep packaging it "for a couple more years, if not decades" ([GNOME X11 FAQ](https://blogs.gnome.org/alatiera/2025/06/23/x11-session-removal-faq/)). Debian trixie builds and security-patches `xvfb`/`xserver-xorg-core` 21.1.16+deb13u4, TigerVNC, x11vnc, Xfce 4.20 and Openbox for amd64 and arm64 ([Debian madison](https://api.ftp-master.debian.org/madison?package=xvfb&s=trixie,forky&text=on)). It also carries **Chromium 154 and Firefox ESR 153 in trixie-security on both architectures** ([trixie-security index](http://security.debian.org/debian-security/dists/trixie-security/main/binary-arm64/Packages.xz)). By contrast, Ubuntu 26.04's archive `firefox` and `chromium-browser` are snap transitional packages ([packages.ubuntu.com](https://packages.ubuntu.com/resolute/firefox)). Google Chrome for arm64 Linux only arrived in July 2026 ([Google](https://blog.google/chromium/bringing-chrome-to-arm64-linux-devices/); [Calibre](https://calibreapp.com/blog/chrome-for-linux-arm64)).

Support length and agent familiarity settle the rest. Debian 13 has security support to **2028-08-09**, LTS to **2030-06-30** and paid ELTS to 2035 ([Freexian](https://www.freexian.com/lts/extended/docs/debian-13-support/)). Fedora 44 gets about 13 months ([Fedora lifecycle](https://docs.fedoraproject.org/en-US/releases/lifecycle/)), and NixOS 26.05 gets **seven months**, to 2026-12-31 ([NixOS 26.05](https://nixos.org/blog/announcements/2026/nixos-2605/)). On Unix & Linux Stack Exchange, `debian` has **16,091 tagged questions against 366 for `nixos`** ([SE API](https://api.stackexchange.com/2.3/tags/debian/info?site=unix)), a rough proxy for how much of each distro the models have seen. Practitioners report that "AI models hallucinate Nix package names" often enough that MCP servers now exist just to query live Nix data ([Codex CLI for Nix](https://codex.danielvaughan.com/2026/05/30/codex-cli-nix-development-mcp-nixos-flakes-reproducible-agent-environments/)). Agents on this machine will install and repair software themselves, so apt fluency matters more than declarative elegance. Ubuntu shares that fluency but adds friction a zero-touch appliance must neutralize: snapd auto-refresh, needrestart prompts that have hung unattended tools ([tui-kit #32](https://github.com/tui-tools/tui-kit/issues/32)), and the 26.04 switch to sudo-rs and Rust coreutils ([Ubuntu 26.04 summary](https://documentation.ubuntu.com/release-notes/26.04/summary-for-lts-users/)).

| Rank | Base | Verdict | Deciding evidence |
|---|---|---|---|
| 1 | **Debian 13 trixie** | Recommended | Patched Xorg/Xvfb on arm64; native Chromium 154 and Firefox ESR; support to 2030; mkosi-supported |
| 2 | Ubuntu 26.04 LTS | Runner-up | Longest free support (to 2031-05-29, [endoflife.date](https://endoflife.date/api/ubuntu.json)) and certified Pi 5 images, but snap browsers and snapd/needrestart hazards |
| 3 | Fedora 44 bootc/Atomic | Best transactional alternative | `bootc upgrade`/`rollback` ([Fedora bootc](https://docs.fedoraproject.org/en-US/bootc/getting-started/)) and Asahi Remix, but ~13-month releases and an X11 future tied to RHEL |
| 4 | NixOS 26.05 | **Rejected for the agent's guest** | Best reproducibility, but seven-month support and hallucinated attribute names |
| 5 | openSUSE Tumbleweed/MicroOS | Niche | Rolling release; Leap 16 already removed Xorg |
| — | Arch, Alpine, Flatcar, Talos | Unsuitable | Arch is officially x86_64-only; Alpine's musl has no Google Chrome ([agent-browser #248](https://github.com/vercel-labs/agent-browser/issues/248)); Flatcar and Talos have no package manager |

### Debian gets NixOS's benefits through tooling, which overturns the earlier pick

NixOS remains the most reproducible system, and its generation rollback is excellent. But on an unattended fleet, its support window forces a major rebase twice a year, and its declarative model is the hardest for an agent to operate ad hoc. Debian recovers most of that value through tooling. mkosi pins its build toolchain with `ToolsTree=` and clamps timestamps with `SourceDateEpoch=` ([mkosi](https://github.com/systemd/mkosi/blob/main/mkosi/resources/man/mkosi.1.md)). systemd-sysupdate, declared non-experimental in systemd v261, delivers A/B image updates; systemd's own reference OS, ParticleOS, uses it with dm-verity on `/usr` ([systemd v261](https://github.com/systemd/systemd/releases/tag/v261); [ParticleOS](https://github.com/systemd/particleos)). Fedora bootc is the strongest alternative for a team that wants transactional OCI-image updates out of the box, at the cost of a 13-month cadence and RHEL's influence over X11.

AgenticLinux's warning that "an agent running `sudo pacman -S` ... is a system administrator with no change control" is fair. This design answers it with snapshots rather than a read-only `/usr`. The agent's guest stays a normal, mutable, apt-managed Debian where the agent has sudo, its work data lives on a separate disk, and "reset to golden" is a hypervisor snapshot rollback ([qm(1)](https://pve.proxmox.com/pve-docs/qm.1.html)). Only the bare-metal host layer underneath, which the agent never touches, is immutable with A/B updates.

Hardware coverage needs two side variants. Debian stable does not support the Raspberry Pi 5; the Debian raspi images say it requires testing or sid ([raspi.debian.net](https://raspi.debian.net/)). Raspberry Pi OS, which is trixie-based, now ships cloud-init on its boot partition ([Raspberry Pi](https://www.raspberrypi.com/news/cloud-init-on-raspberry-pi-os/)), which makes it the natural base for a Pi variant running the same agent userland. Asahi Macs remain a Fedora-only, out-of-scope target. For the day X.Org goes unmaintained, the fallback is a headless wlroots compositor (sway, cage or labwc). These accept prompt-free virtual-pointer input and capture through `ext-image-copy-capture` ([wlr-virtual-pointer](https://wayland.app/protocols/wlr-virtual-pointer-unstable-v1)). GNOME and KDE, by contrast, require a RemoteDesktop portal consent dialog and then a stored restore token, which is too brittle for an image that must never prompt ([Hutterer on libei portals](http://who-t.blogspot.com/2026/07/libei-integrations-in-xdg-remotedesktop.html)).

## Pin an X11 display, then build a thin control daemon

### KasmVNC's Xvnc doubles as the agent's screen and the human's window

Use KasmVNC's Xvnc rather than bare Xvfb, whose runtime resizing is unconfirmed. Xvnc supports RandR resizing and adds a built-in HTTPS/WebSocket web client and WebP/JPEG encoding that adapts to available CPU. It also has data-loss-prevention controls (keystroke and clipboard logging, clipboard size limits, keyboard rate limits) ([KasmVNC configuration](https://kasmweb.com/kasmvnc/docs/latest/configuration.html)) and an owner-only API that toggles each user's read or write permission at runtime ([KasmVNC API](https://github.com/kasmtech/KasmVNC/wiki/API)). **Version 1.5.0 (2026-07-29) ships amd64 and arm64 packages for Debian trixie, Ubuntu noble and Fedora 42/43** and adds H.264/H.265/AV1 video modes ([KasmVNC 1.5.0](https://github.com/kasmtech/KasmVNC/releases/tag/v1.5.0)). Two risks are real. KasmVNC "has broken from the RFB specification", so native VNC clients and Guacamole's VNC backend cannot connect ([KasmVNC README](https://github.com/kasmtech/KasmVNC/blob/master/README.md)), and the project recently moved GitHub organisations. Keep TigerVNC Xvnc plus noVNC as a build-time alternative.

### A working prototype proves the pattern and exposes its gaps

A hands-on examination of a personal prototype, a "desktop" MCP server driving a real desktop, is effectively a working miniature of the proposed system. Display `:1` is a KasmVNC 1.5.0 Xvnc running XFCE. A systemd *user* unit starts it at boot, with lingering enabled and no display manager. The MCP server is a single 259-line Python script run by `uv` that uses FastMCP over stdio. It exposes one `computer` tool with Anthropic's older 17-action vocabulary, drives input through argv-only `xdotool` subprocesses guarded by `--`, and captures with `mss` plus Pillow. Its best idea is a **resolution guard**: if the screen size changed since the model's last screenshot, it refuses coordinate actions and returns a fresh screenshot instead.

The examination showed why that guard matters. A browser viewer had resized the configured 1728×1080 desktop to a 3440×1440 ultrawide, which `-AcceptSetDesktopSize 1` permits. As a result the agent received **1568×656 PNGs at scale 0.456, about 442 KiB each (about 590 KiB as base64)**. Each screenshot took about 130–180 ms to capture, resize and encode, and every action added a fixed 0.5 s settle delay. Coordinates round-tripped exactly, and the cursor was not drawn in screenshots.

The gaps are what an unattended appliance needs most. The server has no authentication and no transport other than stdio, and every subagent shares one process-global coordinate basis. Its synchronous tool blocks FastMCP's event loop for up to 60 s during `wait`, and its modifier handling has a stuck-key bug. It uses the old 1568-px image limits, while the current `computer_toolset_20260801` allows a **2576-px long edge and 4,784 visual tokens** ([Claude computer use docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)). It has no accessibility, window, clipboard, launch or recording tools. Meanwhile the VNC viewer, other remote-desktop tools and xdotool can all inject input into the same display with nothing arbitrating between them. The lesson is to keep the systemd display pattern, the argv-only input path and the resolution guard, to pin the agent's resolution so viewers cannot change it, and to treat authentication, locking and arbitration as core features rather than extras.

### Build agentd, because nothing maintained covers the hard parts

The reuse candidates each fall short. Bytebot is archived. nut.js left public npm for a paid registry, and robotjs and libnut are dead ([nut.js](https://nutjs.dev/blog/i-give-up)). Cua's MIT Rust core and gRPC daemon are capable but coupled to an FSL-licensed product. computer-use-linux is Wayland-first and targets a human's GNOME or KDE session through portals ([computer-use-linux](https://github.com/agent-sh/computer-use-linux)). linux-use is a promising AT-SPI CLI but has no automated tests ([linux-use](https://github.com/javimosch/linux-use)). OSWorld's in-VM server is an unauthenticated Flask benchmark harness ([OSWorld server](https://github.com/xlang-ai/OSWorld/blob/main/desktop_env/server/main.py)).

The prototype shows that input and capture take only a few hundred lines. The value lies in what nobody provides: the coordinate contract, provider adapters, auth, the takeover lease and audit. A custom daemon also carries a hidden cost. Anthropic's prompt-injection classifiers scan screenshots returned through its first-party computer-use tool, not through arbitrary MCP tools ([Claude computer use docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)). `agentd` should therefore also offer a native-toolset adapter, so that API-driven loops executing `computer_toolset_20260801` actions through it keep those classifiers. The verdict is to build a thin daemon and reuse everything around it: KasmVNC for human viewing, Playwright MCP or chrome-devtools-mcp for browser DOM snapshots ([playwright-mcp](https://github.com/microsoft/playwright-mcp); [chrome-devtools-mcp](https://github.com/ChromeDevTools/chrome-devtools-mcp)), and tesseract or OmniParser sidecars for apps with no accessibility tree. Check the licence first, because older OmniParser detectors are AGPL ([OmniParser](https://github.com/microsoft/OmniParser)).

### agentd's contract: frames, coordinates, waits and scoped access

`agentd`'s action vocabulary is the union of the three vendor schemas, which have converged ([OpenAI computer use](https://developers.openai.com/api/docs/guides/tools-computer-use); [Gemini computer use](https://ai.google.dev/gemini-api/docs/computer-use)). It covers click with button, count and modifiers; drag along a path; scroll, type, key, hold and wait; and screenshot and zoom. Every screenshot returns its own metadata. Every input action accepts a `coord_space` (image pixels for Anthropic and OpenAI, normalized 0–999 for Gemini) and an optional `expect_frame_id`. That parameter generalizes the prototype's resolution guard into optimistic concurrency.

```json
{"session":"sess_7f3a","frame_id":4182,"screen":[1280,800],"image":[1280,800],
 "scale":1.0,"coord_space":"image","cursor":[640,412],"format":"png"}
```

Pin the display at a size the model can take without downscaling. Anthropic's visual-token formula is ⌈w/28⌉×⌈h/28⌉. By that formula, the default 1280×800 costs 1,334 tokens, a 1440×900 profile (the size OpenAI's and Gemini's examples use) costs 1,716, and Anthropic's stated ceiling of 1920×1080 costs 2,691. All fit the 4,784-token budget at scale 1.0. Batches follow Anthropic's semantics: execute in order and halt at the first failure. Fixed settle delays (2.0 s in Anthropic's reference code, 0.5 s in the prototype) give way to a `wait_for_stable` call that subscribes to XDamage and returns once the screen has been quiet for a few hundred milliseconds.

For structured observation, expose an AT-SPI element list. Query it narrowly, because each node costs **6–10 D-Bus round-trips**, and the image must enable the accessibility bus and launch Chromium with `--force-renderer-accessibility` ([xa11y quirks](https://xa11y.dev/explanation/accessibility-quirks/)). Expose a Chrome DevTools port that browser MCP servers can attach to. Add tools for windows, clipboard, files, `exec`, `launch` (as a tracked systemd scope) and `set_resolution`. Record with `ffmpeg -f x11grab` alongside an append-only JSONL action log.

Transports split by where the agent runs. Agents inside the VM use MCP over stdio. Remote agents use MCP Streamable HTTP under the stateless 2026-07-28 spec, which replaces protocol sessions with server-minted handles passed as tool arguments ([MCP changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). That design also cures the prototype's shared coordinate basis. Alongside MCP sit REST with OpenAPI, `/adapters/anthropic|openai|gemini` endpoints that accept native tool-call JSON, and a WebSocket stream of frames and events. Locally, authentication rides on a Unix socket checked with `SO_PEERCRED`. Remotely it uses mTLS or short-lived tokens scoped to `observe`, `input`, `exec`, `files`, `takeover` and `admin`, with rate limits and a kill switch.

Start by evolving the proven Python server. Make it async, add a global input lock and in-process XTEST, keep coordinate state per session, and switch to Streamable HTTP, which the installed FastMCP 1.30 already supports along with token verification and DNS-rebinding protection. Once the canonical API stops moving, port the core to Rust. The official `rmcp` SDK already implements the 2026-07-28 spec ([rust-sdk](https://github.com/modelcontextprotocol/rust-sdk)), and x11rb covers XTEST, XShm and XDamage. Accessibility and OCR stay as Python sidecars.

## Humans get in through KasmVNC behind Tailscale, with a takeover lease

Only a few remote-desktop options meet all four requirements: they put the human on the exact display the agent drives, run headless without a GPU, ship arm64 packages and work from a plain browser.

| Option | Shares agent's display | Browser-only | arm64 | Role |
|---|---|---|---|---|
| **KasmVNC 1.5** | Yes (it *is* the X server) | Yes | Yes | **Default** |
| Selkies 2.0 | Yes (attaches to any X display) | Yes | Yes | Add-on: 60 fps H.264 and view-only share links ([Selkies](https://docs.selkies.io/latest/native/)) |
| TigerVNC/x11vnc + noVNC | Yes | Yes | Yes | Fallback when RFB clients or Guacamole are needed |
| Guacamole 1.6 | Via VNC | Yes | Pin `1.6.0` tag | Fleet gateway with in-browser session playback ([Guacamole](https://guacamole.apache.org/doc/gug/recording-playback.html)) |
| GNOME Remote Desktop / KRdp | Only GNOME/KDE Wayland sessions | No | Distro | Reject |
| RustDesk | X11; unattended Wayland is an x86_64 preview ([RustDesk](https://rustdesk.com/blog/unattended-remote-access-wayland/)) | No | Yes | Optional native client |
| Chrome Remote Desktop, TeamViewer, Parsec | Separate session, dummy plug, or no Linux hosting ([Parsec](https://support.parsec.app/hc/en-us/articles/32381494397332-Parsec-App-for-Linux)) | — | — | Reject |

Tailscale is the most turnkey reachability layer, which confirms the earlier suggestion, but three refinements matter. Plain auth keys expire after **at most 90 days** ([Tailscale auth keys](https://tailscale.com/kb/1085/auth-keys)). Bake in a tagged OAuth client secret with the `auth_keys` scope instead, used as `--auth-key='<secret>?preauthorized=true&ephemeral=false'` with `--advertise-tags`. Tagged nodes have key expiry disabled by default, so the box never silently drops off the tailnet ([Tailscale OAuth clients](https://tailscale.com/kb/1215/oauth-clients)). Next, `tailscale serve` publishes the localhost-bound KasmVNC client at `https://<host>.<tailnet>.ts.net` with automatic TLS. It also adds identity headers that `agentd` can log as "who took over" ([Tailscale Serve](https://tailscale.com/kb/1312/serve)). Tailscale SSH, with check-mode re-authentication and session recording, covers the shell ([Tailscale SSH](https://tailscale.com/kb/1193/tailscale-ssh)). Funnel is public and in beta, so avoid it ([Funnel](https://tailscale.com/kb/1223/funnel)). Finally, the tailnet ACL must forbid `tag:agos` from initiating connections, or a hijacked agent can reach every other device on the tailnet.

Alternatives exist for other trust setups. Headscale and NetBird are the self-hosted equivalents ([Headscale](https://github.com/juanfont/headscale/releases); [NetBird](https://docs.netbird.io/manage/peers/register-machines-using-setup-keys)). Cloudflare Tunnel plus Access suits humans who have only a browser and an IdP login, and KasmVNC's web client works behind it. Its tunnel token is a bearer credential, though ([Cloudflare](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/configure-tunnels/remote-tunnel-permissions/)), and Cloudflare's browser-rendered VNC cannot speak KasmVNC's non-RFB protocol.

Takeover has to be arbitrated inside `agentd`, because VNC-level view-only modes restrain only the *human*. The agent injects through XTEST and bypasses the VNC server entirely. The protocol combines OpenClaw's and Bytebot's designs. Viewers start as KasmVNC users without write permission. "Take over" writes a lease in `agentd`, after which agent input fails fast with a typed `HUMAN_IN_CONTROL` error while observation continues, and the same action flips the human to write through KasmVNC's `update_user` API. "Hand back" expires the lease, returns the human to view-only, and invalidates earlier observations, so the agent must take a fresh screenshot before acting ([OpenClaw docs](https://docs.openclaw.ai/nodes/computer-use)). The human's actions are logged as demonstrations ([Bytebot takeover](https://docs.bytebot.ai/guides/takeover-mode)). Automatic pause when a human starts typing would need XInput2 device-source arbitration, for which this research found no published implementation, so it belongs in a later phase.

## One setup script per hypervisor, one cloud-init contract at first boot

### cloud-init NoCloud works everywhere; secrets and duplicates need care

This research confirms and extends the earlier NoCloud suggestion. **cloud-init NoCloud is the only first-boot mechanism with first-class tooling on essentially every target.** Proxmox supports generated drives and `cicustom` snippets, `virt-install` has `--cloud-init`, and Incus has its `cloud-init.user-data` key. VMware uses guestinfo, and a `CIDATA` ISO or VHD covers Hyper-V, VirtualBox, UTM and Parallels. Bare metal and Pi use a FAT partition, which Raspberry Pi OS adopted in November 2025, and clouds use their metadata services ([NoCloud](https://docs.cloud-init.io/en/latest/reference/datasources/nocloud.html); [Raspberry Pi](https://www.raspberrypi.com/news/cloud-init-on-raspberry-pi-os/)). Debian 13 ships cloud-init 25.1.4 and systemd 257 ([sources.debian.org](https://sources.debian.org/src/cloud-init/)). A small `agos-firstboot` unit then reads `/etc/agos/config.toml` and starts the stack. systemd credentials passed through SMBIOS type 11 are a clean secondary channel on QEMU-family hypervisors ([systemd credentials](https://systemd.io/CREDENTIALS/)). On Proxmox, however, the required `args:` option can be set only by `root@pam` ([Qemu.pm](https://git.proxmox.com/?p=qemu-server.git;a=blob_plain;f=src/PVE/API2/Qemu.pm;hb=HEAD)).

Five pitfalls need designing out. If the image carries a `CIDATA` partition and the hypervisor also attaches a seed, two `CIDATA` filesystems exist with undocumented precedence, so label the in-image partition `AGOS` instead. Set `instance-id` explicitly, or edits to user-data re-run per-instance modules and can regenerate SSH host keys ([PVE Roadmap](https://pve.proxmox.com/wiki/Roadmap)). Ship an empty `machine-id`. Never pass secrets on the kernel command line, which is world-readable through `/proc/cmdline`. Delete the Proxmox host snippets once first boot completes.

```yaml
#cloud-config
hostname: agos-01
users:
  - name: agent
    groups: [sudo]
    lock_passwd: true
    ssh_authorized_keys: ["ssh-ed25519 AAAA… you@host"]
write_files:
  - path: /etc/agos/config.toml
    permissions: "0600"
    content: |
      display = "1280x800"
      viewer_listen = "127.0.0.1"
      tailscale_tags = ["tag:agos"]
  - path: /etc/agos/secrets.env
    permissions: "0600"
    content: |
      TS_CLIENT_SECRET=tskey-client-…
```

### Copy community-scripts' unattended mode, not its security shortcuts

The community-scripts project, tteck's successor, is the template for the Proxmox one-liner. Its user-facing repo is thin and sources a shared engine over HTTPS ([core README](https://raw.githubusercontent.com/community-scripts/core/main/README.md)). Its VM scripts run preflight checks (root, PVE 8.x or 9.0–9.2, architecture), and they accept `VM_UNATTENDED=1` plus `VM_*` environment overrides "so a run needs no tty". They cache and checksum images, customize them with `virt-customize`, and use error traps to clean up half-created VMs ([vm-core.func](https://raw.githubusercontent.com/community-scripts/core/main/pve/vm-core.func)). Copy that, but not its root-password SSH, its `-tablet 0` setting that breaks absolute pointing in a desktop console ([debian-vm.sh](https://raw.githubusercontent.com/community-scripts/ProxmoxVE/main/vm/debian-vm.sh)), or its opt-out telemetry, which drew GDPR complaints ([discussion #1836](https://github.com/community-scripts/ProxmoxVE/discussions/1836)).

The script's hygiene follows mature installers. Wrap the body in `main()` called on the last line, because `bash -c "$(curl …)"` never sees curl's exit status, so a truncated or empty download would still run ([Sandstorm](https://sandstorm.io/news/2015-09-24-is-curl-bash-insecure-pgp-verified-install)). Fetch with `--proto '=https' --tlsv1.2` as rustup does ([rustup](https://sh.rustup.rs)). Verify a minisign signature, because even Debian's own cloud images ship unsigned `SHA512SUMS` ([cloud.debian.org](https://cloud.debian.org/images/cloud/trixie/latest/)). Offer `--dry-run`, `--json` and `--yes` with typed exit codes ([Arcjet](https://arcjet.com/blog/designing-a-cli-for-ai-agents)), make re-runs idempotent through VM tags, and gate `--uninstall` behind `--yes`.

```bash
qm create "$VMID" --name agos --ostype l26 --machine q35 --bios ovmf --cpu host \
  --cores 4 --memory 8192 --balloon 0 --scsihw virtio-scsi-single --agent enabled=1 \
  --net0 virtio,bridge=vmbr-agent --vga virtio --tablet 1 --serial0 socket --onboot 1 --tags agos
qm set "$VMID" --efidisk0 local-lvm:0,efitype=4m,pre-enrolled-keys=0 \
  --scsi0 local-lvm:0,import-from=/var/lib/vz/template/cache/agos-1.0.0-amd64.qcow2,discard=on,ssd=1,iothread=1 \
  --scsi1 local-lvm:32 --boot order=scsi0 --ide2 local-lvm:cloudinit \
  --cicustom "user=local:snippets/agos-$VMID-user.yaml"
qm resize "$VMID" scsi0 64G && qm start "$VMID"
```

In these flags, `--tablet 1` gives noVNC an absolute pointer, and `--vga virtio` keeps the graphical console (`--vga serial0` would kill it). `pre-enrolled-keys=0` leaves Secure Boot off. `--cpu host` trades live migration for speed; the GUI default `x86-64-v2-AES` is the cluster-safe choice ([qm(1)](https://pve.proxmox.com/pve-docs/qm.1.html)). Once first boot completes, the script takes the `golden` snapshot that the reset command rolls back to.

Proxmox VE 9.2 for arm64 became official on 2026-08-05. It fully supports NVIDIA Grace and Vera, covers other UEFI Armv9 servers on a best-effort basis, and **does not support Raspberry Pi**. The script therefore detects the host with `dpkg --print-architecture` and uses a 64M EFI disk on arm64 ([PVE Roadmap](https://pve.proxmox.com/wiki/Roadmap)). Flows that use only an API token can fetch the image with `download-url` (content `import`, with a checksum) and create the VM with `import-from`. They cannot upload `cicustom` snippets, because the upload API accepts only ISO, container-template and import content ([PVE API](https://pve.proxmox.com/pve-docs/api-viewer/index.html)). Such flows must use the generated `ciuser` and `sshkeys` fields plus a short-lived enrollment token that the guest exchanges for its full configuration.

## One mkosi recipe builds every image on native runners

**mkosi v27 is the build tool.** It builds Debian, Ubuntu, Fedora, Arch and openSUSE images. It emits disk, UKI, OCI, tar and sysext formats, can use distro-signed bootloaders and shim, and gained El Torito settings that pair with systemd v261's `repart --el-torito` to make hybrid ISOs ([mkosi](https://github.com/systemd/mkosi/blob/main/mkosi/resources/man/mkosi.1.md); [mkosi.news](https://manpages.debian.org/unstable/mkosi/mkosi.news.7.en.html); [systemd v261](https://github.com/systemd/systemd/releases/tag/v261)). Pin its tag, because versions 25 and 26 broke its CLI. If the base were Fedora, bootc with image-builder and Titanoboa would be the right stack ([image-builder](https://github.com/osbuild/image-builder); [Titanoboa](https://github.com/ublue-os/titanoboa)). NixOS now builds images natively, and nixos-generators was archived in January 2026 ([nixos-generators](https://github.com/nix-community/nixos-generators)). live-build produced fully reproducible bookworm live images ([Debian wiki](https://wiki.debian.org/ReproducibleInstalls/LiveImages)), but debos needs `/dev/kvm`, Packer drives installers slowly and non-reproducibly, and Yocto's **140 GB disk and 32 GB RAM** build requirement is overkill when the payload is Chromium, Python and Node from Debian ([Yocto 6.0](https://docs.yoctoproject.org/ref-manual/system-requirements.html)).

### Install to disk only onto a single empty candidate

Every mainstream installer keeps one deliberate safety interlock. Ubuntu asks "Continue with autoinstall?" unless `autoinstall` is on the kernel command line, and then defaults to the largest disk ([Subiquity](https://canonical-subiquity.readthedocs-hosted.com/en/latest/explanation/zero-touch-autoinstall.html)). Proxmox auto-selects its automated entry after a 10-second timeout ([PVE automated install](https://pve.proxmox.com/wiki/Automated_Installation)). systemd-repart defaults to a dry run ([systemd-repart](https://man.archlinux.org/man/systemd-repart.8)).

Ship two ISOs. A live-installer variant boots live and installs only on request. An autoinstall variant says so loudly in its filename and boot menu, and proceeds only when **exactly one** non-removable, non-boot-medium disk of sufficient size exists. It defaults to `systemd-repart --empty=require`, which refuses any disk that already has a partition table. Overwriting a non-empty disk requires an explicit `force` parameter or a serial-number match from a seed stick. Before writing, it shows a cancellable 10-second countdown, and afterwards it reboots into the installed system. VMs consume the disk image directly and never run an installer at all.

### Bare metal runs the agent as a guest of an immutable host

On bare metal, the recommended product is `agos-host`, built from the same recipe. Its disk layout is ESP | usr-A (erofs + verity) | usr-B | var (marked `FactoryReset`). systemd-sysupdate handles updates, and boot counting rolls back a bad one automatically ([sysupdate](https://man7.org/linux/man-pages/man8/systemd-sysupdate.8.html)). `agos-host` runs KVM and the agent's guest image. This is the same health-gated A/B pattern that RAUC (in HAOS) and Rugix (in umbrelOS) prove in appliances. Until `agos-host` matures, x86 users can chain Proxmox's automated installer, whose `answer.toml` supports disk filters and a `[first-boot]` hook, into the setup script ([PVE automated install](https://pve.proxmox.com/wiki/Automated_Installation)). Low-end boxes and the Pi can run the desktop image directly on the hardware, in an explicitly weaker single-layer mode with snapshot or overlay reset.

Secure Boot needs care in 2026. The **Microsoft UEFI CA 2011 expired on June 27, 2026** ([Red Hat](https://access.redhat.com/articles/7128933)), and new aarch64 shims are signed only with the 2023 CA, so older VM NVRAM can reject them ([AlmaLinux](https://almalinux.org/blog/2026-02-18-shim-16.1-update/)). The default boot chain is therefore distro-signed shim → GRUB or systemd-boot → kernel, with no DKMS modules. Secure Boot variants ship separately, as Talos does. Self-signed UKIs are used only where the operator owns key enrollment; systemd-boot auto-enrolls keys in Setup Mode, but only inside VMs ([loader.conf](https://www.mankier.com/5/loader.conf)).

### CI builds each architecture natively and publishes signed artifacts

Since August 2025, native `ubuntu-24.04-arm` runners have been **free for public repos**, with 4 vCPU, 16 GB RAM and a 14 GB SSD ([GitHub changelog](https://github.blog/changelog/2025-08-07-arm64-hosted-runners-for-public-repositories-are-now-generally-available/); [runner specs](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)). Building natively avoids the 4–9× slowdown of QEMU emulation ([Blacksmith](https://www.blacksmith.sh/blog/building-multi-platform-docker-images-for-arm64-in-github-actions)). The pipeline is a two-leg matrix that frees disk space aggressively before building. arm64 runners lack `/dev/kvm`, a request GitHub closed as "not planned" ([runner-images #14062](https://github.com/actions/runner-images/issues/14062)), so aarch64 images are boot-tested under TCG emulation on x64 runners, which do have KVM. Every release also runs the riskiest path: autoinstall onto an empty virtual disk.

Release assets are capped at **2 GiB per file** ([GitHub releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)), so larger files live on R2 or S3. Each release carries `SHA256SUMS` with a minisign signature, cosign signatures and build-provenance attestations. Sysupdate payloads reach the update bucket only after the smoke tests pass. Private repos lose the free arm64 runners and need paid or self-hosted Ampere runners, which also restore KVM for aarch64 boot tests.

| Packages | Snap refreshes (Ubuntu only) | Avoid snaps; otherwise `snap refresh --hold`, since system `refresh.hold` caps at 90 days ([Snap docs](https://snapcraft.io/docs/how-to-guides/manage-snaps/manage-updates/)) |
| Network | Secret prompts; captive-portal UI | Root-owned NetworkManager keyfiles; `[connectivity] enabled=false` ([NetworkManager.conf](https://networkmanager.dev/docs/api/latest/NetworkManager.conf.html)) |
| Clock | Wrong clock breaks TLS | Order services after `time-sync.target` ([time-wait-sync](https://man7.org/linux/man-pages/man8/systemd-time-wait-sync.service.8.html)); `fake-hwclock` on boards without an RTC |
| CLI tools | git, ssh and gpg prompts | `GIT_TERMINAL_PROMPT=0` ([git](https://git-scm.com/docs/git#Documentation/git.txt-GITTERMINALPROMPT)); ssh `StrictHostKeyChecking accept-new` and `BatchMode yes` ([ssh_config](https://man.openbsd.org/ssh_config)); gpg loopback pinentry |
| Identity | Cloned machine-id and host keys | Empty `/etc/machine-id`; SSH host keys generated at first boot ([vm-core.func](https://raw.githubusercontent.com/community-scripts/core/main/pve/vm-core.func)) |
| Self-healing | Hung (not crashed) services; frozen UI | `Type=notify` + `WatchdogSec=` + `Restart=always` ([systemd #38517](https://github.com/systemd/systemd/issues/38517)); a host-side detector for frozen frames and known dialogs that escalates app → session → reboot → snapshot rollback ([kiosk-monitor](https://github.com/extremeshok/kiosk-monitor)) |

## Assume the agent will be hijacked, and keep everything valuable outside its VM

Vendor numbers on prompt injection are improving, but independent attacks keep succeeding. Claude Opus 4.5 held adaptive attackers to a **1%** success rate, which Anthropic still calls "meaningful risk" ([Anthropic research](https://www.anthropic.com/research/prompt-injection-defenses)). At Claude in Chrome's GA, red-team success against Opus 5 was 3.8%, falling to 0% with probes plus a safety classifier ([Claude blog](https://claude.com/blog/claude-in-chrome-generally-available)). Yet in August 2026, researchers turned a "summarize this website" task in Claude Code's auto mode into remote code execution in **3 of 5 runs**, using a downloaded `struct.py` that shadowed Python's standard module. Anthropic replied that auto mode is "a best-effort convenience feature rather than a security boundary" ([CSA research note](https://labs.cloudsecurityalliance.org/research/csa-research-note-claude-code-automode-prompt-injection-2026/)). The pattern goes back to the 2024 "ZombAIs" demo, in which a web page talked Claude's computer-use agent into downloading, `chmod`-ing and running a C2 implant ([Simon Willison](https://simonwillison.net/2024/Oct/25/zombais/)). A machine where the agent has sudo and nobody is watching must be designed for eventual compromise.

Containment therefore comes first, as Anthropic itself prescribes: "containment at the environment layer first, then steer behavior at the model layer". Its Cowork product runs the agent in a full VM where credentials "stay in the host's keychain and never enter the guest machine". Anthropic also found that custom proxies proved more vulnerable than standard primitives ([How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude)). Hence this design uses one VM per agent. Containers are acceptable only when the agent has no sudo and no host mounts, because "the place of a container is inside a VM" ([HN](https://news.ycombinator.com/item?id=49239751)). Firecracker is out, since it has no display device. Every VM gets a golden snapshot with a one-command reset, and work data sits on a separate disk that never holds credentials.

A root agent can flush any firewall inside its own VM, so the setup script builds the egress filter on the host. It creates a dedicated `vmbr-agent` bridge whose nftables rules drop RFC 1918, link-local and metadata (169.254.0.0/16), CGNAT (100.64.0.0/10), loopback and IPv6 ULA destinations before any allow rule. It then permits only a logging HTTP(S) proxy and a filtering resolver ([Munio nftables guide](https://muniod.com/blog/nftables-egress-field-guide.html)). This closes gaps in Anthropic's reference dev-container firewall, which allows DNS and SSH to anywhere and resolves its allowlist IPs once at startup ([init-firewall.sh](https://github.com/anthropics/claude-code/blob/main/.devcontainer/init-firewall.sh)). Browser policy blocks DNS-over-HTTPS so the resolver stays authoritative, and the proxy allowlist starts from Claude Code's documented domains ([network config](https://code.claude.com/docs/en/network-config)).

Credentials fall into three tiers. Tier 0 (hypervisor, homelab-admin and password-manager credentials) never enters the VM. Tier 1 (a `CLAUDE_CODE_OAUTH_TOKEN`, fine-grained GitHub tokens, and a per-VM API key with its own spend cap) is short-lived and injected each boot by cloud-init or `systemd-creds` ([systemd-creds](https://man7.org/linux/man-pages/man1/systemd-creds.1.html)). Tier 2 (web logins) flows through a credential-injecting proxy, or through 1Password and Bitwarden agent flows that require per-task human approval. Bitwarden's SDK is still early alpha ([1Password](https://www.1password.community/announcements-52/august-2026-at-1password-smarter-sign-ins-secure-ai-agents-and-safer-developer-secrets-25431?tid=25431&fid=52); [Bitwarden Agent Access SDK](https://bitwarden.com/blog/introducing-agent-access-sdk/)). Wherever possible, API-driven agent loops run on the host and drive `agentd` remotely, so the model key never enters the guest at all.

Consequential actions (purchases, sending email, publishing, deleting remote data, using credentials) go through an out-of-band approval channel such as a webhook or phone push. In-VM dialogs fail here, because the agent can click them. `agentd` surfaces its "confirm-required" action classes as MCP input requests or HTTP 409 responses, and passes through Gemini's `require_confirmation` decisions. Audit data leaves the VM in real time: auditd execve records, proxy and DNS logs, `agentd`'s JSONL action log with screenshot keyframes, and low-frame-rate screen recordings captured from the host side. Local copies only *detect* tampering through journald's forward-secure sealing ([journald.conf](https://man7.org/linux/man-pages/man5/journald.conf.5.html)), so the off-box record is the authoritative one.

## The recommended architecture separates what the agent controls from what it must never touch

The concrete architecture has two layers. Everything the agent may control lives in its guest. Everything it must never touch (the perimeter, the audit trail, the reset button and the credentials) lives on the host. On an existing hypervisor, the setup script builds the host side; on bare metal, `agos-host` provides it.

```
 Host layer: agos-host on bare metal, or an existing Proxmox/libvirt host
 ┌────────────────────────────────────────────────────────────────────┐
 │ KVM · vmbr-agent bridge + nftables default-deny egress              │
 │ filtering DNS + logging HTTP(S) proxy · off-box log shipping        │

 │ approval webhook · Tailscale on metal (in-guest on other hosts)     │
 │ ┌────────────────────────────────────────────────────────────────┐ │
 │ │ Agent VM "agos-desktop": Debian 13, mutable root + data disk    │ │
```

## Conclusion

The distro turns out to be the least distinctive choice in this project. What makes it a product is three contracts: an observation-and-action contract (frame-stamped coordinates, a pinned resolution, a takeover lease), a provisioning contract (one cloud-init seed honoured on every host), and a containment perimeter that lives outside the guest. Combining "zero input" with "full privilege" forces the security boundary out of the agent's own machine, which is why the bare-metal answer is a host plus a guest rather than a desktop installed on the hardware. The prototype examination makes the same point in miniature. A viewer that silently shrank the agent's view to 0.456 scale and several uncoordinated input paths were not bugs in a 259-line server; they were missing contracts.

Two strategic implications follow. First, the X11 bet is safe through Debian 13's LTS in 2030 but not beyond, so the wlroots backend should exist before Debian 14 and 15 make their Xorg decisions. Second, an MCP-only daemon quietly forfeits Anthropic's first-party screenshot classifiers, which makes the native-toolset adapter a security feature rather than a convenience. Several questions remain open and should be tested first: whether Xvfb supports runtime resizing, how KasmVNC's web client behaves behind `tailscale serve`, cloud-init's precedence when two `CIDATA` volumes are present, whether systemd-sysinstall's unattended mode is ready, and whether XInput2 device data can reliably tell human input from agent input.
